# Realtime server

`server/` (Node 20+, `ws` + `ethers`). Carries **presence and chat**, and stores **room documents** signed by their owners (`rooms.js`). Ownership, items and money live on Monad; the server never holds funds or signs anything. If it is down, nobody loses anything: the client falls back to walking the town alone with the NPC residents.

## Run

```bash
cd server && npm install      # once
node index.js                 # ws://localhost:8767, GET /health for counters
npm test                      # smoke (chat, identity, rooms, invitations, hotel), venues (license, tiers, perks, facades, usernames, guest lists, freeze), migrate, games, exhibition, shop: a mock chain, no network needed except the RPC stand-in
```

Env: `PORT`, `RPC_URL`, `NFT_ADDR`, `ALLOWED_ORIGINS` (comma list; empty = any, dev only), `MAX_PLAYERS`, `MAX_PER_IP`, `DATA_DIR` (reports and `rooms/`; default `server/data`), `ROOM_PREP_MS` / `ROOM_SAVE_MS` (min time between room signatures / saves), `SHOP_ADDRESS` (the deployed ChogShop; empty = the shop is "opening soon"), `SHOP_MOCK=1` (local tests only: purchases recorded in `DATA_DIR/shop/`; never on the live server). The page connects to `ws://<host>:8767`; override with `?server=ws://...`. Preview config `town-server` is in `.claude/launch.json`.

## Deployed (2026-10-08)

Fly.io app `chog-town-ws`, Frankfurt, one `shared-cpu-1x` 256 MB machine that never sleeps (about $2.5 a month plus cents of egress). Address: `wss://chog-town-ws.fly.dev` (`/health` for counters). Config in `server/fly.toml`; the Dockerfile runs as user `node`. Measured from the dev machine: chat A to B about 50 ms, position relay one tick (100 ms).

- Deploy: `flyctl deploy --ha=false --remote-only` from `server/`. `flyctl` is installed in `~/.fly/bin` (not on PATH). `--ha=false` matters: the default would start two machines, and players on different machines would not see each other (the server is single-process by design).
- A deploy onto a machine that crashed past its restart limit leaves it stopped: `flyctl machine start <id>`.
- Logs: `flyctl logs`. Reports are also printed there (`report {json}`), because the container disk is lost on every deploy.
- The live page picks this server automatically (`net.js`); locally it uses `ws://localhost:8767`, and `?server=` overrides both. `ALLOWED_ORIGINS` in `fly.toml` allows only `https://chog-town.pages.dev` and `http://localhost:8766`. This stops other websites from using the server from a visitor's browser; it is not authentication (a script can fake the header). Add any new page address there and redeploy.
- Source of the deployed code: private GitHub repo `boranoyundaa-cmd/chog-town-server` (only `server/`).
- Why a server at all, and why not on-chain: Monad is 300 ms blocks / 600 ms finality (July 2026, MIP-12); 100 players at 10 position updates a second would be 1,000 tx/s, a tenth of the chain's design capacity, each paying gas and a signature. Chat could technically go on-chain but every line would be permanent and paid. Ownership and money stay on-chain.

## Protocol (JSON frames; `server/index.js` header is the source of truth)

Client to server: `auth {addr, sig}` or `auth {session}`, `appear {token|null}`, `logout`, `move {x,z,ry,mv}` (~10/s), `chat {text}`, `report {id, reason}`, `enter {space, who|id, level?, x, z, ry}`, `roomprep {doc}`, `roomsave {doc, ts, sig}`, plus the venue, game, Exhibition and shop frames below (the header of `server/index.js` is the full list).
Server to client: `welcome` (id, challenge, current players, `rooms:1` when the server knows rooms), `join`, `leave`, `appear`, `state` (batched moves, 10 Hz, only players that moved), `snap`, `chat`, `sys`, `authed`, `authfail`, `entered`, `roomprep`, `roomsaved`, `roomfail`, `roomdoc`.

## Mini-games (`server/games.js`)

Score book and match referee, persisted to `DATA_DIR/games.json`. Frames `g_*` (header of the file lists them). Identity = wallet, else the guest id the page keeps in `localStorage` (`g_hello {gid}`). Record games (`stack`, `rhythm`, `daily`) send only the result through `g_score`; limits: stack 0-80 floors, rhythm 20-400 notes and the score is computed from the counts, Daily Chog once per UTC day for today's date, 15 s between submissions. Two-player games (`rps`, `dance`, `c4`, `ls`) run on the server: simultaneous picks are revealed together, moves are validated, timeouts and quits decide. Boards: daily (UTC) and weekly (from Monday), top 10 and your rank; the same two players count at most 5 wins a day. Rewards: no tokens; at most one trophy per game per identity per day (a win against a resident in the browser counts for the trophy only, not the boards), five badges. Both `ENGINE` copies (server and `prototype/js/games.js`) must stay identical.

## Exhibition (`server/exhibition.js`)

Weekly Home contest, Monday 00:00 UTC to Sunday 24:00, with a theme. Frames `ex_list`, `ex_prep` / `ex_submit` (signed entry: a snapshot of your saved Home, replaceable until Sunday 12:00 UTC; replacing with a different Home clears its votes), `ex_voteprep` / `ex_vote` (one signed vote per wallet per week, never for yourself, only wallets with a saved Home, movable until Sunday 24:00; counts hidden until you voted, public once the week is over). The winner (a tie goes to the earlier submission, no winner without a vote) gets a trophy and heads the next week. `enter {space:'hotel', floor:'E'}` is the floor, `enter {space:'exhibit', id}` one entry (read-only). Persisted in `DATA_DIR`.

## Shop (`server/shop.js`)

The server never holds funds or signs. It reads what a wallet owns in the ChogShop contract (`balanceOfBatch`, cached; `shopget`, `shopnotice {tx}` after a purchase forces a fresh read) and enforces what that allows: decor pieces in saved rooms (`room_catalog.json` entries with `shop`), cosmetics worn in extra slots (`equip`, `cos` in every player record), venue budget extras, events (`eventstart`, 24 h, announced in lobby and town), the security camera (`camopen` / `camclose`, a live window of the venue), and tips (`tip {venueId, amount, tx}` checks the `Tip` event of the transaction, then announces it). **Tier locks are enforced here**, not on chain. Catalog: `shop_items.json`, built by `tools/build_shop_catalog.js` from `contracts/items.json`. Contract and deploy: `contracts/README.md`; the owner deploys and sets `SHOP_ADDRESS`.

## Spaces and rooms

Every player is in exactly one **space**: `city` (the town, default on connect), `room:<wallet>` (a saved Home; the owner and invited visitors share it) or `solo:<id>` (a private spot for guests and unsaved rooms), `hotel:<floor>` (0 = lobby 16.5 x 12 m; floors are 24 x 24 m halls; `E` = the Exhibition floor) or `venue:<id>` (a hotel venue: the room document comes from `seed_venues.json` or the owner's signed save; `venue:<id>#2` is the upper level of a two-level venue, a space of its own, so presence and chat are per level and the head count adds both). Presence, movement, chat and `appear` only reach players in the same space; walking limits are per space (town slab 64 x 64 m, `CFG.half` 32 = `HALF` in `world_city.js`, or the room floor: the Home is 20 x 15). `enter` changes space and answers `entered {space, owner, mine, ownerName, doc, savedAt, players}`; `who` is `'me'` (needs a signed-in wallet) or a wallet address. **A Home is private**: entering someone else's needs a direct invitation (`invite {id}`: the owner invites one connected player for 30 minutes; the guest gets `invited {owner, from}`) or the owner's share link token (`enter {..., inv}`; `invlink {renew?}` returns the token, one per owner, 7 days, renewing revokes the old one; stored in `DATA_DIR/invites.json`, `server/invites.js`). Inviting needs a signed-in wallet and a saved Home. A client that does not see `rooms:1` in `welcome` (older server) plays rooms locally; `hotel:1` says the server knows the hotel. The hotel (`server/hotel.js`, v0: only the venues the game itself makes, built by `node tools/build_seed_venues.js`; venue number = floor * 100 + slot): `hotelinfo` answers `hotel {floors, venues, counts}` (no room documents), `enter {space:'hotel', floor}` and `enter {space:'venue', id}` answer `entered` with `floor` / `venue` / `doc`, and `counts {c}` (people inside each venue, real players only) is pushed every 2 s to players on hotel floors when it changed. **Update the `COPY` line of the `Dockerfile` whenever the server gets a new file.**

Saving: `roomprep` returns the cleaned document's hash message and a timestamp, the wallet signs it, `roomsave` is stored only if the signature recovers to the signed-in wallet, matches the cleaned document and is under 2 minutes old. The document is rebuilt from `room_catalog.json` (pieces, themes, window views, patterns; **generated from the game data: `node tools/build_room_catalog.js` after any catalog change**), budget 140 pieces for a Home (a venue gets its tier's), 14 lights, text cleaned, pieces with `minTier` or venue-only pieces dropped where the tier does not allow them, **wall pieces put on their back wall** (`ry` 0 or 90, `z = -D/2` or `x = -W/2`). A save is broadcast to the visitors inside as `roomdoc`. Frames are limited to 2 KB, except `roomprep` and `roomsave` (16 KB).

**Persistence (live since 2026-10-08).** Rooms live in `DATA_DIR/rooms/`; on Fly that is the 1 GB volume `chog_data` mounted at `/data` (about $0.15 a month, daily snapshots kept 5 days; one machine only, a volume belongs to one machine). The volume is mounted root-owned, so the Dockerfile starts as root, `chown`s `/data` and drops to `node` with `su-exec`. A live check (sign in, save, read back) passed; look at the files with `flyctl ssh console -a chog-town-ws -C "ls /data/rooms"`. Deploy the **server before the site**: a new site on an old server still works, rooms then stay local.

## Holder venues, usernames (built 2026-10-09)

- **License** (`license.js`, data `license_data.json` built by `python tools/build_license_data.py` after `build_tokens.py` or `fetch_owners.py`): the server reads `balanceOf` and `ownerOf` on chain (the owner snapshot only says which tokens to check first; a stale snapshot triggers one batched scan of the collection), adds the points per token from the collection's `Tier` trait and gives the tier. Cached 10 minutes per wallet; a fresh read is made when the owner activates.
- **Venues** (`hotel.js`): seed venues from `seed_venues.json` plus one record per holder wallet in `DATA_DIR/venue_meta/<wallet>.json` (tier, `layout: 2`, door number = floor x 100 + first slot (slots 1 to 4 on a floor), `span` 1 / 2 / 4 slots, `levels` 1 or 2, room size, name, kind, description, state `closed`/`open`, rule `public`/`holders`/`list`, guest and ban lists of usernames). The signed rooms and the facade are documents in `DATA_DIR/venue_docs/`, `DATA_DIR/venue2_docs/` (the upper level) and `DATA_DIR/facade_docs/` (same store as Homes, `rooms.js`, but the signed message says "venue", "venue upper level" or "facade", so a Home signature cannot be replayed as a venue). Tier templates (`TEMPLATES` in `hotel.js`, per level; table in `docs/game/world.md`): 1 = 22x16 m, 200 pieces, 16 lights, 1 slot, facade 20 pieces, 12 people inside; 2 = 27x20, 300, 18, a whole wall (2 slots), 40, 20 people, stage and DJ booth; 3 = 27x20, 280, 18, a whole wall on two floors, 2 levels, 60, 32 people, VIP upper level; 4 = 33x22, 340, 22, the whole floor and the one above, 2 levels, 80, 50 people. A slot is 10 m of wall. Capacity is checked on `enter` (the owner always gets in). **Holdings are re-checked** (`hotel.reconcile`): a venue whose owner fell below its tier is **frozen** (closed, decor kept, visitors sent out); it thaws if the tier returns, and after 7 days the slot is freed and the venue archived; `venuemove` upgrades, moves to a smaller room or takes the archive back. **Migration:** venues and Homes saved at the pre-2026-10-15 sizes are shifted into the new rooms when the server starts (`rooms.shiftDoc`: every piece keeps its place against the back walls; `test/migrate.js`). A venue starts **closed** and cannot be opened before its (first-level) room is saved. Slots are taken first-fit (a two-level venue needs the same slots free on the next floor too); numbers never change. Records from the first numbering (8 small slots, smaller rooms, no `layout` field) are re-placed oldest first when the server starts (`test/migrate.js`); their documents are kept, and every wall piece is put back on its wall.
- **Entry** (`hotel.entry`, checked on every `enter {space:'venue'}`): the owner always; closed = refused; banned name = refused; `holders` = the player must appear as their own Chog; `list` = the player's username must be on the list. Closing a venue sends visitors back to its floor.
- **Facade**: a document in a strip 10 m (one slot) or 20 m (two or more) wide and 1.6 m deep; a last rule drops pieces in front of or over the door and wall pieces on the side wall. Sent per floor (`hotelfloor {floor}` -> `facades {floor, items}`) and pushed to the floor when the owner saves.
- **Usernames** (`users.js`): `usernameprep {name}` / `usernamesave {name, ts, sig}`; 3 to 16 characters, starts with a letter, unique ignoring case, reserved and look-alike names refused, one change per 7 days. The username is shown on plates and in chat instead of "Chog #N" or "Guest-NNNN".
- Messages: `venueinfo`, `venuemake`, `venueset`, `venueprep {doc, level?}`, `venuesave {doc, ts, sig, level?}`, `facadeprep`, `facadesave`, `usernameprep`, `usernamesave` (client to server); `venueinfo`, `venuemine`, `venueprep`, `venuesaved`, `facadeprep`, `facadesaved`, `facades`, `username` (server to client). Details in the header comment of `server/index.js`.
- Not built: an anti-rental holding period (decided against by the owner).

## Identity

1. Everyone is a **guest** on connect (default Chog, name `Guest-NNNN`).
2. To appear as Chog #N the wallet signs the server's challenge once (`personal_sign`, free, no transaction); the server recovers the address and checks `ownerOf(N)` on chain. A 12 h session token (kept in `localStorage`, held in server memory) skips the signature on later visits; a server restart means one new signature.
3. One window per Chog: a second login with the same token replaces the first.
4. Traits are not sent by the server; clients load them from the token id (`WALLET.traitsOf`).

## Anti-abuse (v0)

- Movement: positions are clamped to the island and to 1.6x walk speed; repeated violations get a `snap` back. **No building collision on the server yet** (a modified client can walk through walls).
- Chat: 140 chars, burst of 3 per 6 s, repeat text blocked, links and wallet addresses stripped (scam vector in a crypto game). **No word/profanity filter** (owner decision: adult, crypto-native audience); moderation is reports, auto-mute and local mute.
- Reports: written to `server/data/reports.jsonl` with the target's last 5 lines; 3 distinct reporters in 10 min auto-mute the target for 10 min. Players can also mute locally. Nobody reviews the file yet.
- Limits: 6 connections per IP, 200 players, 2 KB frames, Origin allow-list.

## Not done

Server-side collision, backups of the room files, moderation of room text and reported rooms, horizontal scaling (single process, single shard by design), moderator tooling, TLS (put it behind a reverse proxy with `wss://` for deployment; the page picks `wss` automatically on https).
